# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

News-Sentiment-Pipeline is a hands-on, self-directed portfolio project. Goal: demonstrate backend/data/infra engineering depth (not frontend) for backend/data/infra-adjacent job applications. Pipeline concept: ingest financial news → extract ticker/sentiment signals with LangChain → join against historical price data in Databricks → backtest → serve results via a small API + website.

Target stack (per README.md, the plan of record): Postgres (RDS) · Terraform · LangChain · Databricks · Lambda + API Gateway · Datadog · GitHub Actions CI/CD.

README.md contains the full week-by-week (currently Week 1–9) build plan with checkboxes — treat it as the up-to-date roadmap and check it for what's done vs. planned before assuming scope.

## Current state

Infra foundation + a deployed ingestion Lambda exist; still no LangChain extraction, no Databricks job, no API, no CI/CD, no migration tool, no schedule/trigger for the Lambda (invoked manually for now).

Python dependency management is `uv`-based: a root-level `pyproject.toml` + `uv.lock` (single shared `.venv` for all Python/Lambda code, per the single-component convention below). There's still only one Python component (`lambda/news_ingestion/`), so all deps (including scraping deps only that component uses) live in one flat dependency list — revisit splitting into uv dependency groups once a second component with different deps shows up (e.g. a Databricks/LangChain step). `lambda/news_ingestion/requirements.txt` (used for the Lambda zip) is a generated artifact — regenerate it with the command below after any dependency change, never hand-edit it. Note: `trafilatura` pulls in `lxml`, a compiled C-extension; `lambda/news_ingestion/build.ps1` solves the cross-compile problem with `uv pip install --target --python-platform x86_64-manylinux2014 --python-version 3.13 --only-binary :all:`, which fetches prebuilt Linux/cp313 wheels directly on this Windows dev machine (no Docker needed — falls back to building inside `public.ecr.aws/sam/build-python3.13` via Docker if a future dependency lacks a manylinux wheel). The script also excludes `boto3`/`botocore`/`jmespath`/`s3transfer` from the deployment zip even though they're in `requirements.txt` (kept there for local dev) — every AWS Lambda Python runtime already bundles boto3, and botocore's AWS-service JSON data alone is ~19MB, so re-bundling it would nearly double the package for nothing; this cut the zip from ~91MB uncompressed (over half from `babel`'s locale data and botocore) to a 24MB compressed package, comfortably under the 50MB direct-upload limit.

`db/schema.sql` defines the `articles` table (`id, headline, text, url, datetime, tickers, ingested_at`) and has been applied to the live RDS instance. `id` is Finnhub's article id, doubling as the dedup/`source_id` key the README's Week 1–2 plan calls for. `handler.py` now writes to it on every invocation via `db.py`'s `upsert_articles`: `ON CONFLICT (id) DO UPDATE` merges the incoming `tickers` into the existing array (deduplicated union) rather than discarding the row — necessary because the same article can be fetched under multiple tickers, and `related` only ever echoes the ticker that was queried, so merging is the only way an article's `tickers` array reflects more than one ticker. Schema changes still go through `db/schema.sql` + a manual `psql`/`psycopg` run, not a migration tool or Terraform (Terraform's Postgres provider has no clean way to do arbitrary table DDL).

`db/schema.sql` also now defines the `signals` table (`id, ticker, timestamp, event_type, sentiment, confidence, article_ids`), applied to the live RDS instance. Its grain differs from the README's original one-row-per-article sketch: a row is one sentiment-*calculation run* for a ticker, aggregating across every article published that day so far, not one row per article. `timestamp` is when the run executed (not an article's publish time), and `article_ids` (`BIGINT[]`) lists every article the run aggregated over — same array-column convention as `articles.tickers`, with the same caveat that Postgres can't enforce a real FK on array elements, so it's an informal reference enforced only by application code, not the DB. Reruns for the same ticker later the same day (e.g. once more articles arrive) are expected to **append** a new row rather than overwrite, so the table holds a full intraday history of how sentiment evolved — there's no unique business key, just a synthetic `id` PK. `sentiment` is `NUMERIC` (range -1 to 1) rather than a category specifically so it can be quintile-bucketed later per the README's Week 5–6 backtest plan. Nothing writes to `signals` yet — that's Week 3–4 LangChain-extraction scope; this table only exists so far. A `daily_returns` table and a persisted price series (needed to compute the forward returns `daily_returns` would hold) were both deliberately deferred — real gaps in the README's plan, but separate decisions to make later rather than side effects of adding `signals`.

`terraform/` (AWS CLI profile `terraform-user`, region `us-east-1`, local state) provisions:
- `vpc.tf` — data-source lookups (not resources) against the account's pre-existing default VPC and its subnets. No custom VPC/subnets are created here.
- `rds.tf` — one `db.t3.micro` Postgres 16 RDS instance (`news_sentiment` db, single-AZ, 20GB), a DB subnet group, and a security group on port 5432 with **two** ingress rules: the operator's current public IP (auto-detected via a `data "http"` lookup, `checkip.amazonaws.com`, rather than a hardcoded CIDR — this was changed because the repo is public and the user's IP changes across locations; re-run `terraform apply` after switching networks to refresh this rule) for direct `psql`/`run_query.py` access from the laptop, plus a `0.0.0.0/0:5432` rule for the deployed ingestion Lambda (see `lambda.tf` below) — a non-VPC Lambda has no stable/allow-listable IP, so network scoping isn't possible for it; access is instead gated by IAM DB auth rather than network scoping. `publicly_accessible = true` is deliberate for now — flagged to revisit if/when the Lambda moves into the VPC behind a NAT gateway (staying outside the VPC today preserves its default internet egress for the Finnhub API + scraping, which VPC attachment would break without one). `iam_database_authentication_enabled = true` and `apply_immediately = true` are both set — the latter matters because RDS otherwise defers most modifications to the next maintenance window, which silently left `iam_database_authentication_enabled` stuck "pending" after the first `apply` until this was added. IAM auth only covers `lambda_ingestion` (the role it was granted to) — the master user (`var.db_username`) still authenticates by password, so opening `0.0.0.0/0:5432` made it internet-reachable too. `db_password` was rotated to a long random value for this reason (was previously a short, guessable string) — verified live via a fresh `psql`/`run_query.py` connection after the rotation `apply`.
- `lambda.tf` — the deployed ingestion Lambda: an `aws_iam_role` (`AWSLambdaBasicExecutionRole` for CloudWatch Logs, plus an inline policy scoped to `rds-db:connect` on one specific `dbuser` ARN), a `data "archive_file"` zipping `lambda/news_ingestion/build/` (populated by `build.ps1`, see below and Commands), and the `aws_lambda_function` itself (`python3.13`, `x86_64`, not VPC-attached, `timeout = 900` since scraping is sequential per-article and even the `AAPL` smoke test pulls ~90+ articles). Authenticates to RDS via IAM DB auth instead of a password (`db.py`'s `PG_IAM_AUTH` branch, below) — the dedicated, least-privilege Postgres role (`lambda_ingestion`, `SELECT`/`INSERT`/`UPDATE` on `articles` only) is provisioned manually via `db/queries/setup_lambda_iam_user.sql`, not Terraform (the `rds_iam` role only exists once `iam_database_authentication_enabled` is on, and the AWS provider has no resource for Postgres-level roles/grants anyway).
- `variables.tf` (gitignored, not tracked in git) — holds `db_username`/`db_password`/`finnhub_api_key` as variable defaults. Never move real credentials into a tracked `.tf` file.
- Terraform state is local (`terraform.tfstate`, gitignored) — not yet migrated to the S3+lock-table remote backend the README's Week 1–2 plan calls for.

`lambda/news_ingestion/` — Finnhub news ingestion scaffold, chosen over NewsAPI.org/Alpha Vantage (see project history for the tradeoff):
- `finnhub_client.py` — thin wrapper around `finnhub.Client`, `fetch_company_news(client, ticker, from_date, to_date)`.
- `scraper.py` — `fetch_article_text(url)` fetches and extracts full article text via `trafilatura`. Best-effort: paywalled/bot-blocked sites are expected to fail often, logs a warning and returns `None` rather than raising.
- `transform.py` — `to_article_row(article, text)`, a pure mapping (no I/O) from a raw Finnhub article dict + scraped text into the `articles` table row shape. Falls back to Finnhub's `summary` field for `text` when scraping fails, and parses the comma-separated `related` field into a `tickers` list.
- `db.py` — `get_connection()` uses bare `psycopg.connect()` (reads standard `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD` env vars automatically) for local dev, but branches to IAM DB auth when `PG_IAM_AUTH=true` is set (only true in the deployed Lambda's environment): generates a short-lived token via `boto3`'s `generate_db_auth_token` and connects with `sslmode=require`, no `PGPASSWORD` involved. `upsert_articles(conn, rows)` is unchanged (the `ON CONFLICT ... DO UPDATE` merge described above).
- `handler.py` — `lambda_handler(event, context)`, entry point `handler.lambda_handler`. Reads `tickers` from the event, falling back to `DEFAULT_TICKERS` (currently a small hand-trimmed list, intentionally cut down from the original ~100-ticker S&P-100-ish snapshot for faster local runs — expand it back out if a full-universe run is ever needed) when the event omits `tickers` entirely. Per ticker: fetches news, scrapes each article's `url`, transforms, and upserts into `articles` — one DB transaction per ticker, so one ticker's failure doesn't roll back the others. Only the Finnhub fetch call is caught per-ticker (logged, skipped); a DB-layer failure (e.g. missing table, dropped connection) is deliberately left to propagate and abort the whole run rather than being silently swallowed 100 times over. Flat layout (no package nesting) so this directory's contents zip directly as the Lambda deployment package. Returns only `articleCounts`, never the raw scraped rows — the real Lambda runtime `json.dumps()`s the return value after every invocation (unlike `local_run.py`, which just prints locally), and the rows contain non-JSON-serializable `datetime` objects; this also keeps the response well under Lambda's 6MB payload cap.
- The Lambda is now deployed via Terraform (`aws_lambda_function.news_ingestion` in `terraform/lambda.tf`), alongside the still-local `local_run.py` path — invoke manually via `aws lambda invoke` (see Commands) or the console's "Test" button. No schedule/trigger (e.g. EventBridge) is wired up yet, so nothing runs automatically.
- `local_run.py` — runs `lambda_handler` locally. `uv run python lambda/news_ingestion/local_run.py` (no args) hits just `["AAPL"]` for a fast smoke test; `... local_run.py all` omits the `tickers` key entirely so it falls back to `DEFAULT_TICKERS`; `... local_run.py MSFT NVDA ...` runs an arbitrary custom list. A full `DEFAULT_TICKERS` run does real web scraping + DB writes for every article of every ticker and can take a long time — the `["AAPL"]` smoke test alone pulled 176 articles.
- Gitignored `.env` (real `FINNHUB_API_KEY` + `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD`) is for local testing only; `.env.example` is the committed placeholder template — never put real values in `.env.example`.

## Commands

- `cd terraform && terraform init` / `terraform plan` / `terraform apply` — standard Terraform workflow, using the `terraform-user` AWS CLI profile.
- `uv sync` (from repo root) — creates/updates the root `.venv` from `pyproject.toml`/`uv.lock`. Run this instead of manually creating a venv or `pip install`-ing.
- `uv add <package>` — add a new Python dependency (updates `pyproject.toml` + `uv.lock` + `.venv` in one step); follow with the `uv export` command below to keep the Lambda's `requirements.txt` in sync.
- `uv run python lambda/news_ingestion/local_run.py [all|<TICKER>...]` — run the ingestion pipeline locally (reads `lambda/news_ingestion/.env` for `FINNHUB_API_KEY` and the `PG*` DB vars), scraping + upserting into `articles`. No args = `["AAPL"]` only; `all` = the full `DEFAULT_TICKERS` list; or pass explicit tickers.
- `uv export --no-hashes -o lambda/news_ingestion/requirements.txt` — regenerate the Lambda deployment `requirements.txt` from `uv.lock`; re-run after any dependency change, never hand-edit that file.
- `.\lambda\news_ingestion\build.ps1` — packages `lambda/news_ingestion/` for deployment into `build/` (Linux/cp313 wheels via `uv pip install --python-platform`, excluding `boto3`/`botocore`/`jmespath`/`s3transfer` since the Lambda runtime already provides them — see the packaging note above). Re-run before every `terraform plan`/`apply` that should pick up a code or dependency change — Terraform's `archive_file` data source zips whatever's already in `build/` at plan time, it doesn't invoke this script itself.
- `uv run python db/queries/run_query.py <path/to/file.sql>` — run any `.sql` file (schema DDL or ad-hoc queries) against the live RDS instance without needing `psql` installed; prints result rows if the query returns any. Use this for `db/schema.sql` and anything added under `db/queries/` (e.g. `db/queries/urls_by_ticker.sql`, `db/queries/recent_articles.sql`). Calls `conn.commit()` after executing — added because psycopg3 connections default to `autocommit=False`, so without it every DDL/write silently rolled back on `conn.close()` while the script still reported success (exit 0, no error). Discovered while adding the `signals` table: the fix was verified by round-tripping a throwaway probe table through the script before/after the change.
- `uv run python db/queries/run_query.py db/queries/setup_lambda_iam_user.sql` — one-time provisioning of the `lambda_ingestion` IAM-auth Postgres role the deployed Lambda connects as. Must run after a `terraform apply` that turns on `iam_database_authentication_enabled` (RDS's `rds_iam` role doesn't exist before that). Not idempotent — `CREATE USER` has no `IF NOT EXISTS`.
- `aws lambda invoke --function-name news-sentiment-ingestion --cli-binary-format raw-in-base64-out --payload file://payload.json response.json --profile terraform-user --region us-east-1` — manually invoke the deployed Lambda (no schedule/trigger exists yet). Write `{"tickers": ["AAPL"]}` to `payload.json` first — inline `--payload` JSON gets mangled from Windows PowerShell (quoting), so use a file instead, and write it with `[System.IO.File]::WriteAllText(...)` rather than `Set-Content -Encoding utf8`, which adds a BOM the AWS CLI's JSON parser rejects.
- Note: `aws logs tail`/`aws logs filter-log-events` currently fail with a bogus `logGroupName` regex-validation error on this machine (`aws-cli 2.35.20` bundling `Python 3.14.6`) — reproduces even against unrelated, pre-existing log groups, so it's a local CLI bug, not a naming/permissions issue. Use the AWS Console's CloudWatch Logs viewer instead until this is resolved (e.g. a CLI version change).
- No lint/test commands exist yet.

## Working conventions for this project

- This is a learning project: the user owns architecture-level decisions and generally wants hands-on AWS/Terraform steps explained as a tutorial rather than executed directly on their behalf. Plain boilerplate (CLI installs, `.gitignore` edits, formatting) is fine to just do.
- Default to building the smallest next coherent piece and confirming before expanding, even when a request names multiple resources at once (e.g. "DB + 2 Lambdas") — sequence it instead of scaffolding it all in one pass.
- Before adding new Terraform (or other infra-as-code), check what already exists in `terraform/` rather than assuming a clean slate.
- One architecture decision is intentionally still open — surface it again before extending infra rather than assuming an answer: whether to introduce custom private subnets + a NAT gateway or keep using the default VPC's public subnets. The RDS public/private decision is now resolved as a deliberate interim state: the ingestion Lambda stays outside the VPC (preserving default internet egress for Finnhub + scraping without a NAT gateway) and reaches the still-public RDS instance over `0.0.0.0/0:5432`, gated by IAM DB auth rather than network scoping — revisit if/when the Lambda moves into the VPC behind a NAT gateway.
- Do not create pushes or new worktrees unless specifically prompted. Creating a new branch and committing to it is fine — just do not push it.
- All Python dependencies for a component go into a single `requirements.txt`, whether needed for dev or production — no separate `requirements-dev.txt` split.
