# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

News-Sentiment-Pipeline is a hands-on, self-directed portfolio project. Goal: demonstrate backend/data/infra engineering depth (not frontend) for backend/data/infra-adjacent job applications. Pipeline concept: ingest financial news → extract ticker/sentiment signals with LangChain → join against historical price data in Databricks → backtest → serve results via a small API + website.

Target stack (per README.md, the plan of record): Postgres (RDS) · Terraform · LangChain · Databricks · Lambda + API Gateway · GitHub Actions CI/CD.

README.md describes the end-state vision (what the finished pipeline does and why); it deliberately does not track current progress. ## Current state

Three Lambdas are deployed and running on a daily EventBridge Scheduler schedule (`terraform/schedule.tf`, cron timezone `America/New_York` so the EST/EDT switch doesn't silently shift the run time): `news_ingestion` (1am ET), then `sentiment_analysis` (4am ET, after ingestion has had time to finish). `price_backfill` (`lambda/price_backfill/`, yfinance-based) populates a `daily_prices` table and is currently run manually rather than scheduled. A fourth component, `lambda/api/`, is fully written and locally runnable (serves recent `signals` rows) but not yet deployed — no API Gateway or Lambda Terraform resource exists for it yet. A Databricks job/dashboard also exists (reads `signals`/`articles` via JDBC, joins in price data — see `images/DatabricksDashboard*.png`), but it's built directly in the Databricks workspace, not checked into this repo, so treat TODO.md as the source of truth for what it does rather than looking for its code here. Still no CI/CD. A migration tool (Alembic/Flyway) is a deliberate non-goal — `db/schema.sql` + `run_query.py` has handled schema changes fine so far.

Python dependency management is `uv`-based: a root-level `pyproject.toml` + `uv.lock` (single shared `.venv` for all Python/Lambda code across all four `lambda/*` components). `[project.dependencies]` holds deps every component can use (`boto3`, `psycopg`, `pydantic`, etc., plus `news_ingestion`-only scraping deps like `trafilatura`/`finnhub-python`); a `langchain` entry under `[dependency-groups]` holds `sentiment_analysis`-only deps (`langchain`, `langchain-groq`, `langchain-anthropic`, `groq`) so `uv export --only-group langchain` can produce a standalone `requirements.txt` for that Lambda's build without dragging in `trafilatura`/`finnhub-python`. Each `lambda/*/requirements.txt` (used for its Lambda zip) is a generated artifact — regenerate with the command below after any dependency change, never hand-edit it. Note: `trafilatura` pulls in `lxml`, a compiled C-extension; `lambda/news_ingestion/build.ps1` solves the cross-compile problem with `uv pip install --target --python-platform x86_64-manylinux2014 --python-version 3.13 --only-binary :all:`, which fetches prebuilt Linux/cp313 wheels directly on this Windows dev machine (no Docker needed — falls back to building inside `public.ecr.aws/sam/build-python3.13` via Docker if a future dependency lacks a manylinux wheel). The script also excludes `boto3`/`botocore`/`jmespath`/`s3transfer` from the deployment zip even though they're in `requirements.txt` (kept there for local dev) — every AWS Lambda Python runtime already bundles boto3, and botocore's AWS-service JSON data alone is ~19MB, so re-bundling it would nearly double the package for nothing; this cut the zip from ~91MB uncompressed (over half from `babel`'s locale data and botocore) to a 24MB compressed package, comfortably under the 50MB direct-upload limit.

`db/schema.sql` defines the `articles` table (`id, headline, text, url, datetime, tickers, ingested_at`) and has been applied to the live RDS instance. `id` is Finnhub's article id, doubling as the dedup/`source_id` key the README's Week 1–2 plan calls for. `handler.py` now writes to it on every invocation via `db.py`'s `upsert_articles`: `ON CONFLICT (id) DO UPDATE` merges the incoming `tickers` into the existing array (deduplicated union) rather than discarding the row — necessary because the same article can be fetched under multiple tickers, and `related` only ever echoes the ticker that was queried, so merging is the only way an article's `tickers` array reflects more than one ticker. Schema changes still go through `db/schema.sql` + a manual `psql`/`psycopg` run, not a migration tool or Terraform (Terraform's Postgres provider has no clean way to do arbitrary table DDL).

`db/schema.sql` also now defines the `signals` table (`id, ticker, timestamp, event_type, sentiment, involvement, article_ids`), applied to the live RDS instance. Its grain differs from the README's original one-row-per-article sketch: a row is one sentiment-*calculation run* for a ticker, aggregating across every article published that day so far, not one row per article. `timestamp` is when the run executed (not an article's publish time), and `article_ids` (`BIGINT[]`) lists every article the run aggregated over — same array-column convention as `articles.tickers`, with the same caveat that Postgres can't enforce a real FK on array elements, so it's an informal reference enforced only by application code, not the DB. Reruns for the same ticker later the same day (e.g. once more articles arrive) are expected to **append** a new row rather than overwrite, so the table holds a full intraday history of how sentiment evolved — there's no unique business key, just a synthetic `id` PK. `sentiment` is `NUMERIC` (range -1 to 1) rather than a category specifically so it can be quintile-bucketed later per the README's Week 5–6 backtest plan. `lambda/sentiment_analysis/run.py` writes to it daily now via `db.py`'s `insert_signal` (see that section below) — this table is no longer empty scaffolding.

`db/schema.sql` also defines `article_sentiment` (`article_id, ticker, sentiment, involvement, event_type, timestamp`, PK on `(article_id, ticker)`) — the *raw* per-article, per-ticker extraction from `chain.py`, upserted on every run before `combine_chain.py` blends new entries into that ticker's `signals` row. This is a different grain than `signals`: one row per article/ticker here vs. one row per combine-run there. `lambda/sentiment_analysis/price_correlation.py` reads from `article_sentiment` rather than `signals` for correlation analysis specifically because it has far more usable rows. `event_type` was added 2026-08-17 (`db/queries/add_article_sentiment_event_type.sql`) so a combine that failed on one run can be reconstructed from this table and retried on a later run (see `run.py`'s self-healing combine, below) — without it, only `sentiment`/`involvement` survived per article, not enough to rebuild a `TickerSentiment` for `combine_chain.py`. Adding self-healing surfaced a large pre-existing backlog: many rows from 2026-07-01–07-05 and 2026-08-01–08-04 were extracted successfully but never combined into any `signals` row at all — from before `combine_chain.py` had its own model fallback (2026-08-16 fix, see above), a quota-exhausted combine call used to fail silently for the rest of that run. Those rows predate the `event_type` column, so `db.py`'s `fetch_uncombined_sentiment()` substitutes `market_wide_movement` (the designated catch-all `EventType`) for any row where it's `NULL`, rather than raising — it only affects one input line in the combine prompt's context, not anything persisted. The self-healing combine picks this backlog up and folds it into real `signals` rows the next time each affected date is processed.

`db/schema.sql` also defines `article_extraction_attempts` (`article_id, ticker, attempted_at`, PK on `(article_id, ticker)`) — added 2026-08-17 (`db/queries/create_article_extraction_attempts.sql`) to fix a bug where the July sentiment backfill (see `RESUME_SENTIMENT_BACKFILL.md`) made almost no forward progress: `run.py` used to treat an article as "handled" for a ticker only once it appeared in a `signals` row's `article_ids`, but an article whose extraction correctly came back empty (a paywalled/JS-blocked scrape, or the model omitting a ticker) never entered any `signals` row — so it looked "new" again on every subsequent run, forever. `run_backfill`'s per-date retry loop would burn both its attempts and most of its time budget re-processing the same handful of already-settled dates every morning instead of ever reaching new ones. This table records that the chain responded for an `(article_id, ticker)` pair *regardless of what it said* — `fetch_new_articles` now excludes on this table instead of on `signals.article_ids`, and `run.py`'s `mark_attempted()` writes to it for every ticker the chain was asked about on a successful call (an article that fails extraction on every fallback model is deliberately left unmarked, so it's still retried next run).

`db/schema.sql` also defines `daily_prices` (`ticker, date, close`, PK on `(ticker, date)`) — daily closing price only, no OHLC/volume. Populated by `lambda/price_backfill/` (yfinance). The `daily_returns` table (for persisted backtest *output*) is the one piece that's still genuinely deferred — `price_correlation.py` computes forward/same-day returns on the fly from `daily_prices` via `LAG`/`LEAD` rather than persisting them anywhere.

`terraform/` (AWS CLI profile `terraform-user`, region `us-east-1`, local state) provisions:
- `vpc.tf` — data-source lookups (not resources) against the account's pre-existing default VPC and its subnets. No custom VPC/subnets are created here.
- `rds.tf` — one `db.t3.micro` Postgres 16 RDS instance (`news_sentiment` db, single-AZ, 20GB), a DB subnet group, and a security group on port 5432 with **two** ingress rules: the operator's current public IP (auto-detected via a `data "http"` lookup, `checkip.amazonaws.com`, rather than a hardcoded CIDR — this was changed because the repo is public and the user's IP changes across locations; re-run `terraform apply` after switching networks to refresh this rule) for direct `psql`/`run_query.py` access from the laptop, plus a `0.0.0.0/0:5432` rule for the deployed ingestion Lambda (see `lambda.tf` below) — a non-VPC Lambda has no stable/allow-listable IP, so network scoping isn't possible for it; access is instead gated by IAM DB auth rather than network scoping. `publicly_accessible = true` is deliberate for now — flagged to revisit if/when the Lambda moves into the VPC behind a NAT gateway (staying outside the VPC today preserves its default internet egress for the Finnhub API + scraping, which VPC attachment would break without one). `iam_database_authentication_enabled = true` and `apply_immediately = true` are both set — the latter matters because RDS otherwise defers most modifications to the next maintenance window, which silently left `iam_database_authentication_enabled` stuck "pending" after the first `apply` until this was added. IAM auth covers `lambda_ingestion` and `lambda_sentiment` (each Lambda's own least-privilege role — see `sentiment_lambda.tf` below and `db/queries/setup_sentiment_lambda_iam_user.sql`; an `api_read` Postgres role is also provisioned ahead of the still-undeployed API Lambda, per `db/queries/setup_api_iam_user.sql`) — the master user (`var.db_username`) still authenticates by password, so opening `0.0.0.0/0:5432` made it internet-reachable too. `db_password` was rotated to a long random value for this reason (was previously a short, guessable string) — verified live via a fresh `psql`/`run_query.py` connection after the rotation `apply`.
- `lambda.tf` — the deployed ingestion Lambda: an `aws_iam_role` (`AWSLambdaBasicExecutionRole` for CloudWatch Logs, plus an inline policy scoped to `rds-db:connect` on one specific `dbuser` ARN), a `data "archive_file"` zipping `lambda/news_ingestion/build/` (populated by `build.ps1`, see below and Commands), and the `aws_lambda_function` itself (`python3.13`, `x86_64`, not VPC-attached, `timeout = 900` since scraping is sequential per-article and even the `AAPL` smoke test pulls ~90+ articles). Authenticates to RDS via IAM DB auth instead of a password (`db.py`'s `PG_IAM_AUTH` branch, below) — the dedicated, least-privilege Postgres role (`lambda_ingestion`, `SELECT`/`INSERT`/`UPDATE` on `articles` only) is provisioned manually via `db/queries/setup_lambda_iam_user.sql`, not Terraform (the `rds_iam` role only exists once `iam_database_authentication_enabled` is on, and the AWS provider has no resource for Postgres-level roles/grants anyway).
- `sentiment_lambda.tf` — the deployed `sentiment_analysis` Lambda (`news-sentiment-analysis`), same shape as `lambda.tf`: own IAM role + `rds-db:connect` policy (role provisioned via `db/queries/setup_sentiment_lambda_iam_user.sql`), zips `lambda/sentiment_analysis/build/`, `python3.13`/`x86_64`, not VPC-attached, `timeout = 900` (per-article LLM calls fan out via `run.py`'s `ThreadPoolExecutor`, so worst-case runtime scales with a busy day's article count). Environment includes `GROQ_API_KEY`, `GROQ_API_KEY_2` (optional — see `chain.py`'s `GROQ_API_KEYS` below), `ANTHROPIC_API_KEY`, the IAM-auth `PG*` vars, and `TICKERS`.
- `schedule.tf` — puts `news_ingestion`, `sentiment_analysis`, and (temporarily) a `sentiment_analysis` backfill invocation on daily schedules via **EventBridge Scheduler** (`aws_scheduler_schedule`), not the older `aws_cloudwatch_event_rule` — chosen specifically because `schedule_expression_timezone` lets the cron say "1am/4am/5am America/New_York" directly rather than hand-converting to UTC and drifting an hour across the EST/EDT switch. `news_ingestion` runs at 1am ET, `sentiment_analysis` at 4am ET (3 hours of headroom past ingestion's worst-case 900s timeout). All three schedules set `maximum_retry_attempts = 0` — harmless-but-pointless for `news_ingestion` (upserts are idempotent), but load-bearing for `sentiment_analysis`: `signals` has no unique business key, so an overlapping retry would double-insert. A dedicated `aws_iam_role` (`scheduler_invoke_lambda`) lets `scheduler.amazonaws.com` invoke all target function ARNs. `price_backfill` is not on this schedule — still run manually. `aws_scheduler_schedule.sentiment_backfill_daily` is a **temporary** resource (marked as such in a comment in the file itself) invoking the same `sentiment_analysis` Lambda at 5am ET with a fixed `{"backfill_range": [...]}` event to grind through the 2026-07-07–2026-07-31 sentiment-processing gap a bit more each morning, bounded by Groq's account-wide daily token quota — see `RESUME_SENTIMENT_BACKFILL.md` for what it does and when to delete it (both the file and this Terraform resource) once that range is fully backfilled. `handler.py`'s `lambda_handler` branches on `event["backfill_range"]` to call `run.py`'s `run_backfill()` instead of the single-date `run()`; `run_backfill()` derives which dates still need work from the same `fetch_new_articles`-based check `run()` already uses for same-day resumability (no separate progress-tracking table), and stops itself for the invocation once a date comes back with `extracted < candidates` (its return value, along with `candidates`, was added to `run()`'s previously-bare `signal_counts` return) — a heuristic for "the day's Groq quota is probably exhausted" that avoids grinding through the rest of the range on doomed API calls. Before touching the historical range at all, `run_backfill()` now (2026-08-17) first runs the same per-date attempt loop against `date.today() - 1` — the same target_date the 4am ET `sentiment_analysis` run just processed an hour earlier — via a shared `_fill_date()` helper, so a day where the 4am run got quota-starved gets topped up before any of this invocation's remaining time/quota goes toward the old range; on a morning where that alone exhausts the quota, the historical range gets zero progress that day, which is the intended tradeoff (a fresh signal matters more than an old backfill date). This was bundled with the `article_extraction_attempts` fix (see that table's note above) — before it, the range wasn't actually making forward progress at all: every morning's invocation restarted at `start_date` and re-spent both its attempts and most of its time budget on the same handful of already-mostly-processed early dates, since an article whose extraction correctly came back empty never resolved as "done."
- `resource_group.tf` — an `aws_resourcegroups_group` grouping every resource tagged `Project=news-sentiment-pipeline` (via `providers.tf`'s default_tags), so the project's full AWS footprint is viewable in one place regardless of service.
- `outputs.tf` — currently just `rds_endpoint`.
- `variables.tf` (gitignored, not tracked in git) — holds `db_username`/`db_password`/`finnhub_api_key`/`groq_api_key`/`groq_api_key_2`/`anthropic_api_key` as variable defaults. `groq_api_key_2` is optional (defaults to `""`) — a second, separate Groq account for `chain.py`'s two-key rotation, below. Never move real credentials into a tracked `.tf` file.
- Terraform state is local (`terraform.tfstate`, gitignored) — not yet migrated to the S3+lock-table remote backend the README's Week 1–2 plan calls for.

`lambda/news_ingestion/` — Finnhub news ingestion scaffold, chosen over NewsAPI.org/Alpha Vantage (see project history for the tradeoff):
- `finnhub_client.py` — thin wrapper around `finnhub.Client`, `fetch_company_news(client, ticker, from_date, to_date)`.
- `scraper.py` — `fetch_article_text(url)` fetches and extracts full article text via `trafilatura`. Best-effort: paywalled/bot-blocked sites are expected to fail often, logs a warning and returns `None` rather than raising.
- `transform.py` — `to_article_row(article, text)`, a pure mapping (no I/O) from a raw Finnhub article dict + scraped text into the `articles` table row shape. Falls back to Finnhub's `summary` field for `text` when scraping fails, and parses the comma-separated `related` field into a `tickers` list.
- `db.py` — `get_connection()` uses bare `psycopg.connect()` (reads standard `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD` env vars automatically) for local dev, but branches to IAM DB auth when `PG_IAM_AUTH=true` is set (only true in the deployed Lambda's environment): generates a short-lived token via `boto3`'s `generate_db_auth_token` and connects with `sslmode=require`, no `PGPASSWORD` involved. `upsert_articles(conn, rows)` is unchanged (the `ON CONFLICT ... DO UPDATE` merge described above).
- `handler.py` — `lambda_handler(event, context)`, entry point `handler.lambda_handler`. Reads `tickers` from the event, falling back to `DEFAULT_TICKERS` (currently a small hand-trimmed list, intentionally cut down from the original ~100-ticker S&P-100-ish snapshot for faster local runs — expand it back out if a full-universe run is ever needed) when the event omits `tickers` entirely. Per ticker: fetches news, scrapes each article's `url`, transforms, and upserts into `articles` — one DB transaction per ticker, so one ticker's failure doesn't roll back the others. Only the Finnhub fetch call is caught per-ticker (logged, skipped); a DB-layer failure (e.g. missing table, dropped connection) is deliberately left to propagate and abort the whole run rather than being silently swallowed 100 times over. Flat layout (no package nesting) so this directory's contents zip directly as the Lambda deployment package. Returns only `articleCounts`, never the raw scraped rows — the real Lambda runtime `json.dumps()`s the return value after every invocation (unlike `local_run.py`, which just prints locally), and the rows contain non-JSON-serializable `datetime` objects; this also keeps the response well under Lambda's 6MB payload cap.
- The Lambda is deployed via Terraform (`aws_lambda_function.news_ingestion` in `terraform/lambda.tf`) and runs automatically every day at 1am ET via EventBridge Scheduler (`terraform/schedule.tf`) — `local_run.py` and manual `aws lambda invoke` (see Commands) remain available for ad hoc/local runs.
- `local_run.py` — runs `lambda_handler` locally. `uv run python lambda/news_ingestion/local_run.py` (no args) hits just `["AAPL"]` for a fast smoke test; `... local_run.py all` omits the `tickers` key entirely so it falls back to `DEFAULT_TICKERS`; `... local_run.py MSFT NVDA ...` runs an arbitrary custom list. A full `DEFAULT_TICKERS` run does real web scraping + DB writes for every article of every ticker and can take a long time — the `["AAPL"]` smoke test alone pulled 176 articles.
- Gitignored `.env` (real `FINNHUB_API_KEY` + `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD`) is for local testing only; `.env.example` is the committed placeholder template — never put real values in `.env.example`.

`lambda/sentiment_analysis/` — LangChain sentiment extraction, deployed and scheduled (see Current state/Terraform above). Two separate chains:
- `chain.py` — per-article extraction. `SYSTEM_PROMPT` asks the model, for each already-confirmed-relevant ticker in one article, for `sentiment` (-1 to 1), `event_type`, `involvement` (0 to 1, how central the ticker is to the article — not a confidence score), and `reasoning`. `get_llm()` defaults to Groq (`openai/gpt-oss-120b`, cheap while iterating) rather than Anthropic; `extract_with_fallback()` walks `GROQ_MODELS_BEST_TO_WORST` (best-to-worst by rough capability tier) on any failure — a schema violation, a rate limit (each Groq model has its own quota pool), etc. — since getting a usable structured result at all currently matters more than which model produced it. `invoke_with_recovery` also works around Groq's tool-calling API hard-rejecting a whole response on a schema mismatch it could have coerced, by re-parsing the raw failed tool call out of the error body. Swapping to a `claude-*` model id switches to `ChatAnthropic` instead. `GROQ_API_KEYS` (a list built from `GROQ_API_KEY` + optional `GROQ_API_KEY_2`, two separate Groq accounts each with their own independent daily token quota) lets `invoke_with_model_fallback` also rotate keys within each model tier before dropping to a weaker model — added 2026-08-16 after a backfill run burned through the (then-default) `llama-3.3-70b-versatile`'s single-key TPD and, because `combine_chain.py` had no fallback at all at the time, silently produced zero new `signals` rows despite extraction still succeeding on other models (see `combine_chain.py` below). `GROQ_API_KEY_2` is optional — omitting it collapses `GROQ_API_KEYS` to a single-key list, a no-op. `llama-3.3-70b-versatile` and `llama-3.1-8b-instant` were both dropped from `GROQ_MODELS_BEST_TO_WORST` on 2026-08-17 after `groq.Groq().models.list()` showed Groq had removed them from the catalog entirely (404, not a rename) — every call had been wasting a fallback rung retrying both before reaching a live model. `relevant_tickers(article)` (the `articles.tickers ∩ TRACKED_TICKERS` filter, previously duplicated inline in `extract()`/`extract_with_fallback()`) is now a shared helper, also used by `run.py` (see below).
- `schema.py` — Pydantic models bound via `.with_structured_output()`: `TickerSentiment` (one ticker's extraction), `ArticleExtraction` (list of `TickerSentiment`, one per requested ticker, or empty if the scraped text wasn't real content), `EventType` (23-category enum — a specific event like `export_control_or_trade_policy` is preferred over the catch-all `market_wide_movement` whenever the article ties to the ticker through a distinct event), `CombinedSignal` (the second chain's output). `TRACKED_TICKERS` is sourced from the `TICKERS` env var so this component's scope stays in sync with `news_ingestion`'s ticker list without duplicating it. `TickerSentiment.reasoning`/`CombinedSignal.reasoning` are marked `TODO(cut-before-ship)` — kept only for inspecting wrong calls while calibrating against the eval set, not persisted to `signals`.
- `combine_chain.py` — the second chain. `COMBINE_SYSTEM_PROMPT` blends a ticker's previous cumulative signal (if any) with newly-extracted per-article signals into one blended daily `sentiment`/`event_type`, weighting each input by its `involvement` and treating the prior signal as itself carrying the combined weight of every article that already fed into it. `combine_signal()` routes through `chain.py`'s `invoke_with_model_fallback()` (same `GROQ_MODELS_BEST_TO_WORST`/`GROQ_API_KEYS` rotation as `extract_with_fallback()`) when called without an explicit `chain` argument — which is how `run.py` always calls it; the optional `chain` param exists only for pinning a single fixed model (e.g. tests).
- `aggregate.py` — deterministic (non-LLM) helpers used alongside the combine chain: `average_involvement()` (a running weighted mean via previous mean + count as sufficient statistics) and `merge_article_ids()`.
- `run.py` — the orchestrator (`run(target_date)`, called by `handler.py`/`local_run.py`). Defaults to yesterday, not today, since it runs 3 hours after `news_ingestion` (see `schedule.tf`) and yesterday's articles are the complete/stable set by then. Fetches each tracked ticker's never-attempted articles (`db.py`'s `fetch_new_articles()`, now driven off `article_extraction_attempts` rather than `signals.article_ids` — see that table's note above), extracts all candidate articles concurrently (`ThreadPoolExecutor`, `MAX_EXTRACTION_WORKERS = 8` — bounded so a 100+-article day doesn't blow through Groq's per-model rate limit all at once), marks every asked-about ticker attempted via `mark_attempted()`, then builds each ticker's combine input by reading `article_sentiment` back from the DB (`fetch_uncombined_sentiment()` — rows for that ticker/day not yet in the latest signal's `article_ids`) rather than from this run's in-memory extraction results, and writes one `insert_signal` per ticker back on the main thread (the DB connection isn't thread-safe). Reading combine input from the DB instead of from this run's own results is what makes it self-healing: an article whose `combine_signal()` call failed on an earlier run (network error, bad LLM output) is picked up and retried on the next run instead of being silently dropped, since it's still sitting in `article_sentiment` uncombined. `_has_remaining_work()` (used by `run_backfill`, below) checks for both kinds of remaining work — never-attempted articles and extracted-but-uncombined ones — since only checking the first was the root cause of the backfill stall this fixed.
- `db.py` — same `get_connection()` IAM-auth pattern as `news_ingestion/db.py` (duplicated, not imported — each `lambda/*` directory zips independently). `upsert_article_sentiment()` writes raw per-article extractions (now including `event_type`); `insert_signal()` writes the blended daily value; `fetch_latest_signal()`/`fetch_new_articles()`/`fetch_uncombined_sentiment()`/`mark_attempted()` support `run.py`'s incremental, self-healing fetch (see `run.py` above and `article_extraction_attempts` above).
- `price_correlation.py` — `uv run python lambda/sentiment_analysis/price_correlation.py [--horizon 0|1]`. Correlates aggregated daily sentiment (from `article_sentiment`, involvement-weighted, floored at `involvement >= 0.3`) against actual price direction from `daily_prices`: Pearson correlation, plus an accuracy sweep across sentiment thresholds `[0.0..0.5]` compared against the base rate. `--horizon 0` (default) compares same-day close vs. prior close (tests whether extraction reads a day's news the same direction the market already moved — somewhat reactive/circular); `--horizon 1` compares next-day close vs. same-day close (the real forward/tradeable test, needs far more data than currently exists to mean anything). The script's own output explicitly warns not to read the threshold sweep as "the best threshold" — n shrinks at every row, so the fix is more backfilled history (`lambda/price_backfill`), not a finer grid.
- `run_eval.py` + `build_eval_set.py` — a golden-file accuracy harness: `build_eval_set.py` builds `eval_set.csv` from hand-rated known articles, `run_eval.py` runs `extract_with_fallback()` over it and reports MAE, omission rate, and skip agreement — a correctness check against human judgment, separate from `price_correlation.py`'s price-based check.
- `test_fallback.py` — standalone script (not pytest) verifying `invoke_with_model_fallback()`'s rotation logic when a model's simulated quota runs out mid-run.
- `handler.py`/`local_run.py` — same pattern as `news_ingestion`: `lambda_handler(event, context)` reads an optional `event["target_date"]` (or, if `event["backfill_range"]` is present, delegates to `run_backfill()` instead — see the `schedule.tf` entry above); `local_run.py [YYYY-MM-DD]` runs the same `run()` locally (defaults to yesterday). `backfill_run.py [start] [end]` runs `run_backfill()` locally over an explicit date range, mirroring `lambda/news_ingestion/backfill_run.py`'s pattern.

`lambda/price_backfill/` — daily closing-price ingestion via `yfinance`, run manually (not on the `schedule.tf` schedule):
- `yfinance_client.py` — `fetch_price_history(ticker, start_date, end_date)`, thin wrapper over `yf.Ticker(ticker).history(interval="1d")`.
- `transform.py` — `to_price_rows()` maps the yfinance DataFrame's `Close` column into `daily_prices` row dicts.
- `db.py` — `upsert_daily_prices()`, `ON CONFLICT (ticker, date) DO UPDATE SET close = EXCLUDED.close`. Same duplicated IAM-auth `get_connection()` pattern as the other components.
- `local_run.py` — `uv run python lambda/price_backfill/local_run.py TICKER [start_date] [end_date]` (default lookback 365 days).

`lambda/api/` — written and locally runnable, **not yet deployed** (no API Gateway or Lambda Terraform resource exists for it):
- `handler.py` — `lambda_handler(event, context)` reads `queryStringParameters.limit` (default 50, capped at 200) and returns `fetch_recent_signals()` as an API-Gateway-proxy-shaped response (`statusCode`/`headers`/`body`) so wiring up API Gateway later shouldn't require touching this handler again.
- `db.py` — `fetch_recent_signals()` joins each `signals` row to its articles' headlines via a correlated subquery over `article_ids` (a JOIN would need an unnest + re-aggregate for no benefit, since `article_ids` is an array).
- `local_run.py` — `uv run python lambda/api/local_run.py [limit]`, invokes the handler locally and pretty-prints the JSON body.

## Commands

- `cd terraform && terraform init` / `terraform plan` / `terraform apply` — standard Terraform workflow, using the `terraform-user` AWS CLI profile.
- `uv sync` (from repo root) — creates/updates the root `.venv` from `pyproject.toml`/`uv.lock`. Run this instead of manually creating a venv or `pip install`-ing.
- `uv add <package>` — add a new Python dependency (updates `pyproject.toml` + `uv.lock` + `.venv` in one step); follow with the `uv export` command below to keep the Lambda's `requirements.txt` in sync.
- `uv run python lambda/news_ingestion/local_run.py [all|<TICKER>...]` — run the ingestion pipeline locally (reads `lambda/news_ingestion/.env` for `FINNHUB_API_KEY` and the `PG*` DB vars), scraping + upserting into `articles`. No args = `["AAPL"]` only; `all` = the full `DEFAULT_TICKERS` list; or pass explicit tickers.
- `uv export --no-hashes -o lambda/news_ingestion/requirements.txt` — regenerate the Lambda deployment `requirements.txt` from `uv.lock`; re-run after any dependency change, never hand-edit that file.
- `.\lambda\news_ingestion\build.ps1` — packages `lambda/news_ingestion/` for deployment into `build/` (Linux/cp313 wheels via `uv pip install --python-platform`, excluding `boto3`/`botocore`/`jmespath`/`s3transfer` since the Lambda runtime already provides them — see the packaging note above). Re-run before every `terraform plan`/`apply` that should pick up a code or dependency change — Terraform's `archive_file` data source zips whatever's already in `build/` at plan time, it doesn't invoke this script itself.
- `uv run python db/queries/run_query.py <path/to/file.sql>` — run any `.sql` file (schema DDL or ad-hoc queries) against the live RDS instance without needing `psql` installed; prints result rows if the query returns any. Use this for `db/schema.sql` and anything added under `db/queries/` (e.g. `db/queries/urls_by_ticker.sql`, `db/queries/recent_articles.sql`). Calls `conn.commit()` after executing — added because psycopg3 connections default to `autocommit=False`, so without it every DDL/write silently rolled back on `conn.close()` while the script still reported success (exit 0, no error). Discovered while adding the `signals` table: the fix was verified by round-tripping a throwaway probe table through the script before/after the change.
- `uv run python db/queries/run_query.py db/queries/setup_lambda_iam_user.sql` — one-time provisioning of the `lambda_ingestion` IAM-auth Postgres role the deployed Lambda connects as. Must run after a `terraform apply` that turns on `iam_database_authentication_enabled` (RDS's `rds_iam` role doesn't exist before that). Not idempotent — `CREATE USER` has no `IF NOT EXISTS`.
- `aws lambda invoke --function-name news-sentiment-ingestion --cli-binary-format raw-in-base64-out --payload file://payload.json response.json --profile terraform-user --region us-east-1` — manually invoke the deployed Lambda on demand, outside its normal daily EventBridge Scheduler run (`terraform/schedule.tf`). Write `{"tickers": ["AAPL"]}` to `payload.json` first — inline `--payload` JSON gets mangled from Windows PowerShell (quoting), so use a file instead, and write it with `[System.IO.File]::WriteAllText(...)` rather than `Set-Content -Encoding utf8`, which adds a BOM the AWS CLI's JSON parser rejects.
- Note: `aws logs tail`/`aws logs filter-log-events` currently fail with a bogus `logGroupName` regex-validation error on this machine (`aws-cli 2.35.20` bundling `Python 3.14.6`) — reproduces even against unrelated, pre-existing log groups, so it's a local CLI bug, not a naming/permissions issue. Use the AWS Console's CloudWatch Logs viewer instead until this is resolved (e.g. a CLI version change).
- `uv run python lambda/sentiment_analysis/local_run.py [YYYY-MM-DD]` — run sentiment extraction + combine locally (defaults to yesterday), reading `lambda/sentiment_analysis/.env`.
- `uv run python lambda/sentiment_analysis/backfill_run.py <start YYYY-MM-DD> <end YYYY-MM-DD>` — run `run_backfill()` locally over a date range (see `RESUME_SENTIMENT_BACKFILL.md`); works forward through whichever dates in the range still have unprocessed articles and stops once a date's Groq quota looks exhausted.
- `uv run python lambda/price_backfill/local_run.py TICKER [start_date] [end_date]` — backfill/refresh `daily_prices` for one ticker (default 365-day lookback).
- `uv run python lambda/sentiment_analysis/price_correlation.py [--horizon 0|1]` — correlate extracted sentiment against actual price direction; see the `price_correlation.py` description above for what the two horizons mean.
- `uv run python lambda/sentiment_analysis/run_eval.py` — run the hand-rated golden-set accuracy eval (MAE, omission rate, skip agreement) against current extraction.
- `uv run python lambda/api/local_run.py [limit]` — run the (not-yet-deployed) API handler locally and pretty-print recent signals.
- No pytest suite exists yet — `run_eval.py` (extraction accuracy vs. a hand-rated set) and `test_fallback.py` (model-fallback rotation logic) are the only test-shaped tooling so far, both ad hoc scripts rather than a real test runner.

## Working conventions for this project

- This is a learning project: the user owns architecture-level decisions and generally wants hands-on AWS/Terraform steps explained as a tutorial rather than executed directly on their behalf. Plain boilerplate (CLI installs, `.gitignore` edits, formatting) is fine to just do.
- Default to building the smallest next coherent piece and confirming before expanding, even when a request names multiple resources at once (e.g. "DB + 2 Lambdas") — sequence it instead of scaffolding it all in one pass.
- Before adding new Terraform (or other infra-as-code), check what already exists in `terraform/` rather than assuming a clean slate.
- One architecture decision is intentionally still open — surface it again before extending infra rather than assuming an answer: whether to introduce custom private subnets + a NAT gateway or keep using the default VPC's public subnets. The RDS public/private decision is now resolved as a deliberate interim state: the ingestion Lambda stays outside the VPC (preserving default internet egress for Finnhub + scraping without a NAT gateway) and reaches the still-public RDS instance over `0.0.0.0/0:5432`, gated by IAM DB auth rather than network scoping — revisit if/when the Lambda moves into the VPC behind a NAT gateway.
- Do not create pushes or new worktrees unless specifically prompted. Creating a new branch and committing to it is fine — just do not push it.
- All Python dependencies for a component go into a single `requirements.txt`, whether needed for dev or production — no separate `requirements-dev.txt` split.
